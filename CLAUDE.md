## Mattgab AI Leasing Agent: Project Guide

Compiled 2026-07-13 for Claude Code. This file orients any engineer, human or AI, picking up this project cold. It covers the vision, current state, roadmap, and open problems. Technical reference detail (repo layout, deploy mechanics, environment map) is in the second half.

If you are Claude Code running an audit: read this whole file before touching code. The "Where We're Stuck" and "Audit Focus Areas" sections below are your starting checklist, not the full list. Assume there are more problems than what's written here.

---

### 1. Vision

Mattgab Management runs two Phoenix apartment communities, NMFA and Windsong. The leasing team (Jenea, Michel, Yanelia, Felipa, Stephany, Angel) spends a large share of its week on repetitive work: answering the same qualifying questions on every call, texting the same tour and application links, chasing the same maintenance requests to the portal, reconciling the same delinquency numbers by hand.

The goal of this project is to automate that repetitive layer, specifically an AI voice agent that answers property phone lines, qualifies callers, and texts the right link at the right moment, plus a small set of dashboards and reports that replace manual spreadsheet work, so the human team can spend more of its time on the work a person actually needs to do: building community, making tenants feel at home, and handling anything that requires judgment.

Every decision on this project should be weighed against that goal. A feature that saves the AI agent time but creates more manual monitoring work for Jenea is a net loss. A feature that is clever but not safe (sends a text without consent, quotes a unit that does not exist, exposes tenant data) is not acceptable even if it saves time, because it creates cleanup work and erodes trust faster than it saves anything.

Two standing rules from the project owner govern all work here, not just this file:
- Everything should be done with deep research and triple-checked code and process. Do not guess, especially on anything involving APIs, ad platforms, digital operations, or technical workflows. Look it up.
- Research how property management companies are automating leasing work, and prefer proven patterns over inventing new ones.

### 2. Where We Are Now (as of 2026-07-13)

**Live in production today:**

The AI voice agent (`mattgab-voice`, Railway project `charismatic-joy`, `main` branch, Twilio + Anthropic Claude Haiku 4.5) answers both property lines: NMFA at 520-600-6936 and Windsong at 520-800-0759. As of today it has a two-layer SMS consent gate (a tightened intent-detection regex plus a server-side `isConsentAffirmative` check that requires the caller's own words to be an explicit yes before a tour or application link goes out), a fix for a bug that let the wrong property's number text a caller (Twilio's Messaging Service Sender Pool was auto-picking the sender instead of the property's own number), a proactive offer to text the maintenance portal link instead of waiting for the resident to ask, and crash resilience so one caller's API error can no longer take down every other active call on the server.

A public dashboard (`mattgabmanagement.com/nmfamgmt-portal1943.html`) shows occupancy, delinquency, move-in/move-out, leads, and expirations, pulling live from Rent Manager via `rm-api.php` and lead data via `lead-api.php`. It has known security gaps, see Section 3.

A WordPress chatbot writes leads into `wp_paa_leads` via `lead-api.php`. Facebook lead capture exists but the real-time webhook has been dead since June 13; a manual stopgap script auto-sends routine Facebook replies in the interim, and Meta App Review for the real fix was submitted 2026-07-13. Real recovery for actual prospects is not expected until early August even if the review itself clears sooner. Caution for whoever checks this next: the webhook's own debug log started showing successful sends again on 2026-07-11, but every one of those went to one of two known test or developer account IDs, not a real prospect, so log activity alone is not proof the webhook is back. Facebook Marketplace is a separate problem the webhook fix will not touch at all: Marketplace listing messages land in a seller-profile inbox with no API, invisible to both the webhook and the stopgap script, so those leads are funneled instead through an AI text-line CTA added directly to the active listing descriptions, a workaround that stays in place permanently, not just during the outage.

A weekly call-scoring report, an AI voice performance report, and a daily audit process all run, each with its own accuracy checks against Rent Manager's controller reports.

**Recently shipped (today, 2026-07-13):** the SMS consent gate and the three bugs found while testing it (wrong sender, missing proactive portal offer, interrupt handling that could re-ask already-answered questions and, separately, crash the whole server on any Claude API hiccup). Full record in project memory `project_sms_consent_gate_deployed`.

**Architecture direction:** as of 2026-05-05 the plan is to move to Knock CRM as the system of record, piloting on Windsong first, then NMFA 60 days later, while keeping the Twilio AI voice agent as a vendor-isolated front end that posts leads into Knock. This was decided using a "handoff lens": if Jenea leaves, can a non-technical successor run this system without her. The current five-system stack (Twilio/Railway custom code, Apps Script, Mailchimp, WordPress chatbot, Facebook webhook) fails that test. See `project_ai_architecture_path` for the full reasoning and the five questions used to evaluate CRM vendors.

### 3. Where We're Stuck

Grouped by what kind of problem it is, not by urgency, since the audit should judge severity independently.

**Security.** The dashboard's data endpoints are unauthenticated even though the page itself sits behind HTTP Basic Auth. `rm-api.php` is the worst case: it returns roughly 340KB of Rent Manager data, including prospect PII, with `Access-Control-Allow-Origin: *`, meaning any website can read it cross-origin from a visitor's browser. `leads-summary.php` is similarly open. `lead-api.php` is better protected (403s without a key) but the valid key is hardcoded client-side and passed in a URL query string, so it leaks into logs and browser history. None of this has been fixed yet; the fix direction is written up but deliberately not yet deployed because it needs validation with the hosting contractor first. Full detail in `project_dashboard_endpoint_audit`.

**Data accuracy.** The dashboard's delinquency number does not match Rent Manager's controller report (27 vs. 8 for Windsong in one comparison) because it counts gross late charges without netting waived or credited amounts. A real fix needs the net account balance, which means pulling payments and credits, not just charges. This same definitional gap cascades into the Performing vs. Non-Performing Units metric Michel now sees on the dashboard (a unit counts as non-performing if it is vacant or the tenant owes $1,000 or more): counted on the controller's current-tenant basis it is 11 NMFA and 4 Windsong non-performing, counted on the dashboard's active-plus-collections basis it is 13 NMFA and 3 Windsong. Nobody has decided which basis is authoritative before this number goes to ownership, and that decision should happen before the delinquency fix, not after, since the fix will move both numbers again. The Expirations tab has a related counting problem: for the same lease window the dashboard showed 24 distinct tenants expiring against the controller's 13 NMFA and 7 Windsong, because the dashboard's expirations feed can carry a unit's prior, superseded lease term alongside its current one instead of filtering to just the active lease; a confirmed example is one NMFA unit that shows two different tenant names across the expirations and delinquency feeds for what is actually one current tenancy. Separately, the "Last 60 Days" move-in/move-out cards on both the dashboard and the daily report email actually show year-to-date figures, because the cutoff date in `rm-api.php` is hardcoded to January 1 instead of a rolling 60-day window. And 51% of year-to-date move-ins have no lead source recorded in Rent Manager at all, with Zillow specifically under-credited (35 first-touch leads but only 1 tagged source), which distorts any "what's working" analysis pulling from that data. Zillow's own YTD lead count is separately just low on its own terms, 3 leads on the Base package against 144 total Rent Manager prospects; a Signature package upgrade was evaluated and declined 2026-07-13 for lack of clear ROI at that volume, so Zillow's real contribution to the lead mix should be read as genuinely small, not only under-attributed.

**Lead pipeline data quality.** Every Zillow inquiry currently writes two to three rows into `wp_paa_leads` for the same prospect, a duplicate pair created in the same second plus a later row that carries the phone number, which pollutes name fields and fragments contact data across rows. None of those Zillow rows get an `ai_summary`, so there is currently no way to confirm from the data whether the Zillow auto-reply actually fired for any of them. Separately, the AI conversation audit rubric used to score call and chat quality still lists retired pricing ($1,100, $1,500, $1,800) instead of the current two-tier pricing matrix in Section 7, which means audit scores against that rubric may currently be marking correct AI answers as wrong.

**AI accuracy.** A caller was quoted 1-bedroom availability at NMFA when zero 1-bedroom units were actually vacant, only four 2-bedroom units were. Deferred rather than quick-patched, because the right fix is wiring live Rent Manager inventory into the AI's responses, not another hardcoded guard. Worth noting: this was reported against staging, and a later branch comparison found that the `main` (production) branch already has a hardcoded "temporarily unavailable" guard for NMFA 1-bedrooms that staging never received. Whether that guard is still accurate, and whether the same problem exists for Windsong's unit types, has not been re-verified since. Tracked as task #27.

**Deploy and release process.** The `staging` and `main` branches of `mattgab-voice` drifted apart independently for an unknown period: `main` received newer pricing and unit-mix content that `staging` never got, while `staging` received the SMS safety fixes that `main` lacked. This was caught by diffing before a production push, not by any process that would catch it automatically. There is currently no branch-parity check, no CI, and no automated test suite; every verification (`node --check`, brace and paren counts, targeted grep, a hand-built test table for the consent function) is done manually, by hand, per change. That is a process risk independent of any single bug.

**Standing operational gaps not yet closed:** the health-monitor Apps Script fix (false alarms plus one silently-dead probe) has conflicting status in the project record itself, one note says it was written but never deployed, another says it was deployed and verified live on 2026-06-22 with three edits confirmed persisted after reload in the Apps Script editor. This needs a direct check against the live script at script.google.com before anyone acts on it either way, since assuming the wrong answer means either re-doing a fix that already shipped or skipping one that never did. A fix for a dashboard key mismatch that makes "AI Channel Leads" always show zero is written but not deployed. Both Apartments.com listings appear to be dark as of July 9 with the cause unconfirmed. A tour reminder and no-show system is built but blocked on upgrading both Calendly accounts off the Free plan. Two weeks of AI voice performance reports are built but undeployed because FileZilla was unreachable. None of these are audit findings exactly, they are known and tracked, but an auditor should confirm they are still accurately described and not stale.

**Decisions still open:** whether and how to migrate to Knock CRM has a direction (Section 2) but no committed date. The maintenance automation proposal (Rent Manager Tenant Web Access plus Property Meld, roughly $415 to $520 per month) is drafted for Michel but not decided; it is phased, not a single yes or no, phase one turns on Rent Manager's native resident portal, phase two pilots Property Meld at NMFA, phase three scales to Windsong plus a KPI dashboard view, and none of the three phases has been approved yet. The Zillow leads historical backfill has an analysis-first plan but has not been executed. Underneath several of these sits an unresolved hosting constraint: Owain's team has said they will not host the custom dashboard and lead tool on Mattgab's current WordPress hosting plan, since it falls outside their scope and the plan is close to its 5GB storage cap. Any fix that assumes these tools stay on the current host, including the dashboard security fix above, may need a hosting decision first, not just a code change.

**Prospect texting is built but not live.** The intent to connect with every lead that provides a phone number is not yet realized in production. A prospect SMS drip (Welcome message plus three nudges on Day 0, 2, 5, and 9) was built to run against every lead landing in `wp_paa_leads`, engine at `current/apps-scripts/prospect-drip.gs`, still shipping with `DRY_RUN=true` and gated by `DRIP_START_ISO`. Work paused 2026-06-03 to prioritize the dashboard and was not picked back up. Platform split: Twilio owns the prospect funnel since leads already live in `wp_paa_leads` wired to Twilio and the AI voice agent; Rent Manager owns rent reminders and debt collection since RM holds the ledger and fires balance-threshold notices against the tenant record. One open safety gap in the drip itself: `sms-webhook.php` answers inbound texts but does not stamp the lead as "replied," so a reply from a prospect will not halt the drip on its own; opt-out handling and the Day 9 cap are the only safety net until that hook is wired. Full detail in `project_texting_initiative`.

### 4. Where We're Going

Near term: close the security gaps in Section 3 (dashboard endpoints), finish and deploy the standing fixes already written (health monitor, key mismatch), decide the false-availability fix approach for the AI voice agent, and keep the Build Playbook (Section 6) current as each of these lands.

Mid term: execute the Knock CRM pilot on Windsong, evaluate against the five vendor-handoff questions in `project_ai_architecture_path`, and if it holds up, begin the retirement schedule for the custom stack in this order: Zillow auto-reply, Facebook Messenger webhook, WordPress chatbot, Mailchimp automation, keeping the Twilio AI voice agent running longest since it is the most differentiated and safest to run in parallel with a new system.

Longer term, if this system holds up at Mattgab, the Build Playbook exists specifically so it can be redeployed for other small property management clients without reverse-engineering the first build.

### 5. Goals and Deadlines

A few concrete numbers and dates are driving decisions elsewhere in this project and are easy to lose track of since they live scattered across sessions.

NMFA had a vacancy target of 22 units by June 1, 2026, NMFA-only, not a combined Mattgab number, Windsong runs its own separate metrics and is not part of this goal. As of the last confirmed data point, May 13, NMFA sat at 36 vacant with 5 pre-leases locked, projected to 31 by June 1, and with 151 NMFA leases expiring within 90 days the realistic move-in need was closer to 12 to 15 units, not the raw 9-unit gap between 31 and 22. Whether NMFA actually reached 22 by June 1 has not been re-confirmed since; check the live dashboard before this goal is cited again in the audit or anywhere else. The broader trajectory Michel set was below 32 vacant by the start of May, 22 by June, below 10 after that.

The Google Ads consultant engagement has a follow-up review meeting around 2026-07-23 to confirm which conversion action the new Performance Max campaign is optimizing toward, and whether GA4 conversion data is actually flowing into `wp_paa_leads` with usable attribution rather than being self-reported by Google alone.

The NMFA Google review score has tiered targets: roughly 8 more 5-star reviews reaches 3.5 stars, roughly 35 reaches 3.7, roughly 94 reaches 4.0. A maintenance-close review request email already exists and fires natively off Rent Manager, so the identified lever is conversion and measurement of that existing send, plus two new, non-duplicative moments, lease renewal and move-in, that have not launched yet, NMFA first, Windsong second once it has its own review link. Review gating, asking only residents likely to leave a positive review, is explicitly prohibited by both Google policy and an FTC rule with real financial penalties, so any automation here has to ask every resident the same way, not a filtered set.

Facebook Messenger's real recovery is not expected until early August 2026 even though Meta's App Review process itself may resolve sooner; see Section 2 for why webhook debug-log activity alone is not proof of recovery.

### 6. Repo and Environment Reference

**Code:** GitHub `nmfa1943/mattgab-voice`. Two branches matter: `staging` and `main`. They have diverged before without anyone noticing until a diff was run; do not assume they are in sync.

**Hosting:** Railway, two separate projects. `remarkable-light` contains the `staging` environment (`mattgab-voice-staging.up.railway.app`, tracks the `staging` branch) and an orphaned `production` environment that is not the real one. `charismatic-joy` contains the actual production environment (`mattgab-voice-production.up.railway.app`, tracks `main`). Both auto-deploy on push.

**Phone numbers:** NMFA AI line 520-600-6936, Windsong AI line 520-800-0759. Both are Twilio numbers on the "Mattgab Production" Twilio account. A Messaging Service pool contains both numbers, which is why `sendSms()` must always pass an explicit `from` alongside `messagingServiceSid`, otherwise Twilio can pick the wrong property's number as sender.

**Deploy procedure that has worked reliably:** fetch the live raw file from the target branch, build the patch locally as a targeted string replacement (never a full-file overwrite unless branch parity has just been confirmed), verify with `node --check`, brace and paren balance counts, and targeted grep checks before touching anything live, apply the change through GitHub's web editor, then re-fetch the raw file after commit and diff it against the locally verified version to confirm the live file matches exactly before considering Railway's auto-deploy trustworthy. If live-testing against staging by repointing a Twilio number's webhook, revert the webhook immediately after testing since real callers hit staging while it is repointed.

**Dashboard and lead pipeline:** `mattgabmanagement.com/nmfamgmt-portal1943.html` calls `rm-api.php`, `lead-api.php`, `leads-summary.php`, and related report endpoints on the same host. Hosting and security fall to a contractor (Owain) whose scope is explicitly hosting and security only, not application code; the application code itself (`rm-api.php`, dashboard, webhook logic) is drafted in these AI-assisted sessions and deployed by Jenea via FileZilla, not by Owain.

### 7. Source of Truth Documents

`Mattgab_AI_Build_Playbook.docx`, in the shared project folder, is the repeatability doc for standing up this whole stack from scratch. It should already reflect prerequisites, the lead pipeline, the delinquency and move report, the AI voice agent, Zillow auto-reply, the weekly call report, operational runbooks, cost breakdown, a new-client checklist, what was deliberately not automated, and lessons learned the hard way. It is a standing task to update this doc every time the project advances; if today's SMS and voice fixes are not yet reflected there, that update is still owed.

`Mattgab_AI_Leasing_Source_of_Truth.docx` is the doc that must be updated first, before any AI prompt change anywhere, with a sweep across all channels afterward. If the AI voice agent's actual behavior does not match what this document says it should do, that is itself an audit finding.

Property-specific facts an auditor will need to check the AI against: NMFA offers 1-bedroom and 2-bedroom units only, Windsong offers 2-bedroom and 3-bedroom only. Current move-in concession structure, confirmed 2026-07-09: NMFA 2-bedroom is $750 off the deposit on a 12-month lease only, no concession on the 6-month $1,295 term; Windsong 2-bedroom is $1,400 total move-in ($900 deposit plus $500 first month). 1-bedroom and 3-bedroom concessions are unconfirmed. Whether these were fully swept into the live AI prompts has not been confirmed as of this writing, task #14.

### 8. Audit Focus Areas

For whoever runs the audit, in rough priority order: confirm the dashboard endpoint exposure in Section 3 is still live and scope its actual severity (what real tenant or prospect data is exposed, not just that it is exposed); check whether `staging` and `main` have diverged again since 2026-07-13; verify the AI voice agent's live behavior against the source-of-truth documents in Section 7, specifically pricing, concessions, and unit availability by property; check whether the crash-resilience fix from today (`stream.on('error')`) is the only unhandled-error path in `server.js`, or whether similar gaps exist elsewhere in the file; review whether the delinquency and lead-attribution data problems in Section 3 are display bugs only, or indicate a deeper problem in how `rm-api.php` queries Rent Manager; resolve the health-monitor Apps Script deploy-status conflict in Section 3 by checking the live script directly; confirm whether the Zillow lead duplication described in Section 3 is still writing two to three rows per inquiry; and confirm the NMFA 22-vacant-by-June-1 goal outcome in Section 5 against current dashboard numbers.

Treat every claim in this file as a starting hypothesis, not a conclusion. It was compiled from project notes taken across several months of sessions; some of it may be stale by the time this audit runs. Verify against the live code and live systems before acting on anything written here.
